1// ====== RCPP BLACKLISTED METHOD NAMES ======
2//
3// Avoid using these names for any method exposed via RCPP_MODULE:
4//
5// - initialize
6// - finalize
7// - show
8// - call
9// - dim
10// - length
11// - names
12// - levels
13// - plot
14// - print
15// - summary
16// - mean
17// - median
18// - quantile
19// - any other common S4 or base generic
20//
21// Why?
22// These names are intercepted by R's S4 / S3 method dispatch system.
23// Your methods will either:
24// - not show up at all
25// - be silently ignored
26// - be replaced by base R behavior
27// - give mysterious errors when calling from R
28//
29// Recommendation:
30// - Always use custom or non-conflicting names.
31// - E.g., use "init" instead of "initialize", "print_line" instead of "print".
32//
33//
34// Source:
35// Rcpp FAQ + StackOverflow + blood, sweat, and tears.

37// ====== R OBJECT COPYING GOTCHAS ======
38//
39// When accessing nested objects in R (e.g., fishery$population$method()),
40// R creates temporary copies. Any modifications made through such calls
41// will be lost because they modify the temporary copy, not the original object.
42//
43// Example of the problem:
44// fishery$population$modifier() # Modifies a temporary copy
45// print(fishery$population) # Original remains unchanged
46//
47// To avoid this:
48// 1. Don't expose methods that modify state through nested objects
49// 2. Expose modification methods at the top level (e.g., fishery$modifyPopulation())
50// 3. If you must modify nested objects in R, use intermediate assignment:
51// pop <- fishery$population
52// pop$modifier()
53// fishery$population <- pop
54//
55// However, this behaviour appears to be limited to functions. Directly setting nested
56// object members appears to work. E.g.,
57//
58// fishery$pop$par$n <- new_n # works
59//
